## 一、LLM 基础概念

### 1.1 必须能讲清的名词

- **Token**:模型处理文本的最小单位,计费和上下文长度都按 token 算。中文通常 1 个汉字约 1~2 个 token。
- **上下文窗口(Context Window)**:模型一次能"看到"的最大 token 数(输入 + 输出)。超出就必须截断或摘要。
- **temperature**:控制随机性。越低越确定(适合工具调用、结构化输出),越高越发散(适合创作)。
- **top_p**:核采样,只在累计概率达到 p 的候选词里采样。一般 temperature 与 top_p 只调一个。
- **幻觉(Hallucination)**:模型生成看似合理但不真实的内容。原因:模型本质是预测下一个 token,不是查事实。

### 1.2 ⭐ 如何减少幻觉
1. RAG:让答案基于检索到的真实资料
2. Prompt 里要求"不知道就说不知道""只根据给定资料回答"
3. 降低 temperature
4. 要求给出引用来源,并做后置校验
5. 关键结论用工具(查库、调接口)获取,而不是让模型"记忆"

### 1.3 Prompt 基础
- **消息角色**:system(设定身份与规则)、user(用户输入)、assistant(模型回复)。
- **Prompt 四要素**:指令、上下文、输入数据、输出格式。
- **Few-shot**:给几个示例,让模型模仿格式和风格。
- **CoT(Chain of Thought)**:引导模型分步推理,复杂问题准确率更高。
- **结构化输出**:要求返回 JSON,配合 schema 校验;校验失败则带错误信息重试。

## 二、⭐⭐ Function Calling / Tool Calling(重中之重)

### 2.1 完整流程
1. 开发者定义工具:名称、描述、参数 schema
2. 把工具定义随用户问题一起发给模型
3. 模型判断是否需要调用工具,返回"要调用哪个工具 + 参数"(**模型自己不执行**)
4. 应用程序执行对应的方法
5. 把执行结果作为一条 tool 消息回传给模型
6. 模型结合结果生成最终回答(也可能继续调用下一个工具)

> 一句话:**模型负责决策,应用负责执行。**

### 2.2 提高调用准确率
- 工具名称语义清晰,描述写明"什么时候该用、什么时候不该用"
- 参数含义、取值范围、示例写在参数描述里
- 工具数量不要太多(太多会干扰选择),必要时按场景动态注入
- 返回结果精简、结构清晰,避免把大段无关数据塞回上下文

### 2.3 异常与兜底
- 参数校验失败:返回明确的错误信息,让模型有机会修正后重试
- 超时/下游故障:设置超时、限次重试、降级返回
- 模型不调用工具:检查工具描述、system prompt 是否明确、模型本身是否支持
- 幂等与权限:有副作用的工具(下单、转账)必须做权限校验和二次确认

### 2.4 Spring AI 对应
- `@Tool` 标注方法,`@ToolParam` 描述参数
- `ChatClient` 注册工具后,框架自动完成"调用 → 执行 → 回传"循环

## 三、⭐⭐ Agent 原理

### 3.1 Agent 是什么
能围绕目标**自主规划、调用工具、观察结果、迭代直到完成任务**的系统。

核心循环:**感知 → 思考 → 行动 → 观察 → (重复)**

### 3.2 Agent vs Workflow
| | Workflow | Agent |
|---|---|---|
| 流程 | 开发者预先写死 | 模型动态决定 |
| 可控性 | 高 | 较低 |
| 成本/延迟 | 低 | 高(多轮调用) |
| 适用 | 流程固定、可预测 | 步骤不确定、开放任务 |

**结论**:能用 Workflow 解决的不要上 Agent。

### 3.3 ⭐ 常见模式
- **ReAct**:Reasoning + Acting 交替。想一步、做一步、看结果再想。
  - 优点:灵活、可解释
  - 缺点:步数多、成本高、容易走偏或陷入循环
- **Plan-and-Execute**:先整体规划步骤,再逐步执行,必要时重规划。
  - 优点:全局性更好、更省调用
  - 缺点:计划可能不适应中途变化,需要重规划机制
- **Reflection**:执行后让模型自我检查、修正。

### 3.4 ⭐ 防止死循环 / 失控
- 最大步数(max iterations)
- 总超时、总 token/成本上限
- 检测重复的工具调用(同工具同参数多次)
- 关键节点人工确认(Human-in-the-loop)
- 失败时优雅退出并告知用户

## 四、⭐⭐ RAG(检索增强生成)

### 4.1 完整链路
**离线阶段**:文档加载/解析 → 清洗 → 切分(chunk)→ Embedding → 写入向量库
**在线阶段**:用户问题 → (query 改写)→ Embedding → 向量检索 topK → (重排序)→ 拼入 Prompt → 模型生成

### 4.2 关键概念
- **Embedding**:把文本映射成向量,语义相近的文本向量距离近。
- **相似度**:常用余弦相似度。
- **向量库**:pgvector、Milvus、Weaviate 等。至少熟悉一个。

### 4.3 切分策略
- 固定长度 + 重叠(overlap):简单,重叠避免语义在边界被切断
- 按结构切分:按标题、段落、句子
- chunk 太大:检索不精准、占上下文;太小:语义不完整
- 每个 chunk 附带元数据(来源、章节、时间),便于过滤和引用

### 4.4 ⭐ 检索效果不好怎么排查
1. 先看**检索到的内容对不对**(问题在检索还是在生成)
2. 切分是否合理(chunk 大小、重叠)
3. Embedding 模型是否适合该语言/领域
4. 加**元数据过滤**缩小范围
5. **混合检索**:向量 + 关键词(BM25)
6. **Rerank**:先多召回再用重排模型精排
7. **Query 改写**:把口语化问题改写成更适合检索的形式
8. 调整 topK 和相似度阈值
9. 建立测试问题集,量化对比每次优化

### 4.5 RAG vs 微调
- RAG:知识经常更新、需要引用来源、成本低、上手快
- 微调:改变模型的风格、格式或特定能力;不适合频繁更新的事实性知识
- 两者可以组合

## 五、对话记忆(Memory)

- **短期记忆**:当前会话的历史消息,放在上下文里。
- **长期记忆**:跨会话保存的用户信息/事实,存库后按需检索注入。
- **上下文过长的处理**:
  - 滑动窗口只保留最近 N 轮
  - 对早期对话做摘要
  - 关键事实单独抽取保存
- **后端视角(你的优势)**:
  - 会话 ID / 用户 ID 隔离
  - Redis 缓存热点会话,数据库持久化
  - 设置过期策略,控制存储与 token 成本
- Spring AI:`ChatMemory` + Advisor

## 六、MCP(Model Context Protocol)

- **是什么**:一套标准协议,让 AI 应用以统一方式接入外部工具和数据源。
- **角色**:MCP Client(嵌在 AI 应用中)、MCP Server(暴露工具/资源/提示词)。
- **解决的问题**:每个工具单独适配 → 统一协议,一次实现,多处可用。
- **和 Function Calling 的区别**:
  - Function Calling 是**模型层面**"如何表达要调用什么"的能力
  - MCP 是**应用与工具之间**"如何发现和调用工具"的协议
  - 二者互补:MCP 提供工具,模型通过 Function Calling 决定何时调用
- 建议:自己写一个简单的 MCP Server 并接入 demo。

## 七、多 Agent 与编排

- **常见模式**:主管-下属(Supervisor)、流水线、评审/辩论
- **难点**:任务拆分、状态传递、失败重试、结果聚合、成本控制
- **状态机思路**:用明确的状态和流转条件管理多步任务,可控、可恢复、可观测(可迁移你做过的状态机设计)
- **Human-in-the-loop**:高风险节点暂停,等人确认后继续
- 不必一上来就多 Agent:单 Agent + 好工具通常已够用

---

## 八、⭐ 工程化(后端的主场)

- **流式输出**:SSE,降低用户感知延迟
- **异步任务**:耗时 Agent 任务走消息队列(RabbitMQ),结果回调或轮询
- **限流、超时、重试、降级**:防止大模型接口波动拖垮系统
- **成本与延迟优化**:
  - 缓存(相同问题、Embedding 结果)
  - 模型分级:简单任务用小模型,复杂任务用大模型
  - 精简 Prompt 与上下文
- **可观测性**:请求日志、trace、token 用量、每步工具调用记录
- **评估**:
  - 构建测试集,记录期望输出/期望工具调用
  - 指标:任务完成率、答案准确率、工具调用正确率、延迟、成本
  - 线上抽检 + 用户反馈

## 九、安全

- **Prompt 注入**:用户或外部内容(网页、文档)里夹带恶意指令,试图覆盖系统规则。
  - 防护:区分系统指令与外部数据、对外部内容加隔离标记、输出校验、限制工具权限
- **工具权限最小化**:只暴露必要的工具;写操作/高危操作二次确认
- **敏感信息**:密钥、隐私数据不放进 Prompt;日志脱敏
- **越权**:工具执行时用**当前用户的权限**校验,而不是 Agent 的全局权限

## 十一、项目话术模板(agent-demo)

面试时按这个顺序讲:

1. **背景**:做了一个什么 Agent,解决什么问题
2. **架构**:画图讲清 ChatClient → 工具 → 记忆 → RAG → 流式输出
3. **亮点**:
   - Tool Calling 的异常兜底
   - Redis 会话记忆 + 持久化
   - RAG 的切分与调优
   - MQ 异步任务 / 状态机编排(后端优势)
4. **踩坑故事(准备 3 个)**:
   - 模型不调用工具 / 调错工具,怎么排查和修复
   - 检索召回不准,怎么定位并优化
   - 上下文超长,怎么处理
5. **结果**:有量化就量化(如准确率从 X 提升到 Y、响应时间、token 节省)
