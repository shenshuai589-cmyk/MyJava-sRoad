
## TLAB(Thread Local Allocation Buffer)

TLAB（Thread Local Allocation Buffer，线程本地分配缓冲区）是 Java 虚拟机（JVM）为了解决多线程并发分配内存效率低下问题而设计的一种内存分配优化机制。

### **核心原理**

在 JVM 中，新创建的对象通常会在堆内存的 **Eden 区** 分配空间。因为 Eden 区是所有线程共享的，如果多个线程同时申请分配内存，就必须通过加锁（或 CAS 原子操作）来保证线程安全，这在频繁创建对象时会导致严重的竞争和性能开销。

为了解决这个问题，JVM 在 Eden 区为每个线程预先划出一块独立的私有内存区域，这就是 **TLAB**：

- **独占分配**：每个线程在自己的 TLAB 内分配内存，不需要加锁，也不存在并发竞争，分配速度极快（仅需移动指针，即 Pointer Bumping）。
    
- **共享读取**：TLAB 只是**分配**私有，对象分配完成后，其他线程依然可以正常访问和读取该对象。
    

### **工作流程与大对象处理**

1. **优先 TLAB 分配**：当线程尝试创建新对象时，首先检查自己的 TLAB 剩余空间是否足够。
    
2. **空间不足时的策略**：如果对象大小超过了 TLAB 的剩余空间，JVM 会判断该对象是否“太大型”：
    
    - **对象过大**：直接绕过 TLAB，在公共 Eden 区（通过加锁/CAS 操作）进行分配。
        
    - **对象不大**：丢弃（或退回）当前的 TLAB，向 Eden 区申请一块新的 TLAB 空间，并将对象放入新 TLAB 中。

## 指针碰撞

- **工作原理**：当 Java 堆中的内存是绝对规整的（即所有已分配的内存放在一边，空闲内存放在另一边），中间由一个指针作为分界线。分配内存时，只需将分界线指针向空闲内存区域移动一段与对象大小相等的距离，这一过程即为指针碰撞。
    
- **适用场景**：取决于垃圾回收器是否带有压缩/整理（Compacting）功能。采用复制算法或标记-整理算法的收集器（如 Serial、ParNew、G1/ZGC 在 Young GC 复制存活对象时）分配内存均采用指针碰撞。如果内存不规整（如 CMS 采用标记-清除算法），则只能使用空闲列表（Free List）分配。
    
- **并发安全保障**：在多线程环境下并发移动指针会导致线程不安全，JVM 主要通过两种方式保障：
    
    1. **TLAB（线程本地分配缓冲区）**：每个线程在 Eden 区预分配私有空间，在自己的 TLAB 内通过指针碰撞无锁分配。
        
    2. **CAS + 失败重试**：当 TLAB 空间用尽或未开启时，JVM 采用 CAS 原子操作配合重试更新指针，保证内存分配的原子性。
        

**逃逸分析与栈上分配的关系**

- **逃逸分析（Escape Analysis）**：JVM 在 JIT 编译阶段执行的一项优化分析技术，用于确定对象的作用域是否会逃出当前方法或线程：
    
    - **不逃逸**：对象仅在当前方法内部创建和使用，方法结束后不再被访问。
        
    - **方法逃逸**：对象作为返回值或参数传递给其他方法，但不会超出当前线程。
        
    - **线程逃逸**：对象被赋值给类变量或可被其他线程引用的实例变量。
        
- **栈上分配（On-Stack Allocation）**：
    
    - **核心关系**：逃逸分析是实现栈上分配的**前提条件**。只有当逃逸分析判定一个对象**完全不逃逸**时，JVM 才会考虑将该对象分配在线程栈的**栈帧**上，而非堆内存中。
        
    - **技术收益**：栈上分配打破了“所有对象都在堆上分配”的常规策略。由于栈帧在方法调用结束时直接出栈销毁，栈上的对象内存也会随之自动释放，**无需垃圾回收器（GC）介入**，大幅降低堆 GC 的频率和停顿时间。
        
- **HotSpot JVM 的具体落地**：HotSpot 实际上并未直接在栈帧中分配一整块连续内存作为对象实体，而是通过逃逸分析触发**标量替换（Scalar Replacement）**——将不逃逸的对象拆解为若干基本数据类型（标量），直接分配在栈帧的局部变量表中，从而达到了与栈上分配等价的性能效果。

## 空闲列队


当 Java 堆中的内存**不规整**（已用内存和未用内存交错在一起）时，JVM 无法使用简单的移动指针方式分配内存。此时，JVM 会维护一个记录表（即空闲列表），其中记录了哪些内存块是可用的。

在创建新对象时：

1. **查找空间**：JVM 在空闲列表中找到一块足够容纳该对象的内存区域。
    
2. **划定分配**：将该区域划分给新对象。
    
3. **更新列表**：更新空闲列表上的记录，去掉已被使用的空间或修正剩余的大小。
    

### **空闲列表 vs 指针碰撞**

|**比较维度**|**指针碰撞（Pointer Bumping）**|**空闲列表（Free List）**|
|---|---|---|
|**内存规整度**|绝对规整（已用与未用由指针隔离）|不规整（已用与未用碎片化交错）|
|**垃圾回收算法**|复制算法、标记-整理算法|标记-清除算法（Mark-Sweep）|
|**分配效率**|极高（仅需移动指针）|较低（需要遍历列表检索合适大小的块）|
|**典型收集器应用**|Serial、ParNew、G1/ZGC（复制阶段）|CMS（Concurrent Mark Sweep）|

### **常见分配策略（内存检索算法）**

在使用空闲列表寻找合适内存块时，JVM 常见的检索算法包括：

- **首次适应（First Fit）**：从头开始遍历空闲列表，找到**第一个**大于等于对象大小的内存块就直接分配。速度快，但容易在列表头部留下小碎片。
    
- **最佳适应（Best Fit）**：遍历整个空闲列表，找到能够容纳对象的**最小**内存块。能最大化节省大内存块，但检索慢，且易产生极微小的不可用碎片。
    
- **最坏适应（Worst Fit）**：找到当前**最大**的空闲内存块进行切分。切分后的剩余部分依然较大，适合中等大小对象的分配。

## 锁升级

Java 对象头中的 **Mark Word** 记录了当前对象的锁状态。锁升级按照 **无锁 → 偏向锁 → 轻量级锁 → 重量级锁** 的顺序单向演进：

1. **无锁（Unlocked）**
    
    - **状态**：对象刚创建，尚无任何线程对其加锁。
        
    - **标志位**：`01`（偏向标志位为 `0`）。
        
2. **偏向锁（Biased Lock）**
    
    - **场景**：锁总是被**同一个线程**多次获取，不存在多线程竞争。
        
    - **原理**：JVM 将对象头 Mark Word 中的线程 ID 改为当前线程 ID。后续该线程再次进入同步块时，**无需执行任何 CAS 操作**，仅需对比线程 ID 即可直接获取锁，开销几乎为零。
        
    - **标志位**：`01`（偏向标志位为 `1`）。
        
3. **轻量级锁（Lightweight Lock）**
    
    - **场景**：存在**少量线程交替竞争**锁，且持锁时间极短。
        
    - **原理**：当第二个线程尝试获取偏向锁时，偏向锁被撤销并升级为轻量级锁。未拿到锁的线程不会被挂起（阻塞），而是通过 **CAS 自旋（Spinning）** 不断重试获取锁，从而避免了用户态与内核态的上下文切换。
        
    - **标志位**：`00`。
        
4. **重量级锁（Heavyweight Lock）**
    
    - **场景**：**多线程强竞争**，或单线程自旋重试达到阈值（自适应自旋）。
        
    - **原理**：轻量级锁膨胀为重量级锁。JVM 会在底层为其分配一个 `ObjectMonitor` 对象，未竞争到锁的线程会被**休眠并放入等待队列**，由操作系统管理其阻塞与唤醒（涉及用户态与内核态切换）。
        
    - **标志位**：`10`。
        

### **重要补充与特性**

- **单向不可逆**：锁升级过程是不可逆的（只能升级，不能降级），这样可以消除锁状态来回切换带来的性能损耗（唯二例外是 GC 垃圾回收回收锁对象或安全点撤销时重置状态）。
    
- **偏向锁的退场（JDK 15+）**：由于偏向锁的撤销（Revocation）需要等待安全点（STW，Stop-The-World），在现代多核高并发应用中，偏向锁撤销的开销往往大于其带来的收益。因此 JDK 15 默认废弃了偏向锁，JDK 18+ 进一步进行了移除。


## **Minor GC**（又称 Young GC）是指发生在 Java 堆中新生代（Young Generation）的垃圾收集行为。

根据“弱分代假说”（绝大多数 Java 对象都是朝生夕灭的），Minor GC 的发生非常频繁，回收速度也极快。

**1. 新生代内存布局**

新生代被划分为三个区域（默认比例为 **8:1:1**）：

- **Eden 区**：新创建的对象绝大多数在此分配内存。
    
- **Survivor 0 区（S0 / From Space）**：上次 GC 后存活下来的对象暂存区。
    
- **Survivor 1 区（S1 / To Space）**：GC 时作为接收存活对象的空闲缓冲区。
    

**2. Minor GC 的触发条件**

- **唯一直接触发条件**：当 **Eden 区空间不足/装满** 时，JVM 就会触发一次 Minor GC。
    
- **注意**：Survivor 区满了不会主动触发 Minor GC，而是在 Eden 区满触发 GC 时，Survivor 区的对象顺带被处理。
    

**3. 执行过程（标记-复制算法）**

Minor GC 核心采用**标记-复制（Copying）算法**，具体步骤如下：

1. **标记存活对象**：利用可达性分析，从 GC Roots 出发，扫描标记 Eden 和 S0（From）区中的存活对象。
    
2. **复制到 To 区**：将 Eden 和 S0 中标记为存活的对象复制到 S1（To）区，并将它们的**对象年龄 $+1$**。
    
3. **清空旧区域**：直接清空 Eden 和 S0 区的内存空间。
    
4. **角色互换**：S0 与 S1 互换身份，原先的 S1（To）变成下一次 GC 的 S0（From），而原先的 S0 变为下一次 GC 的空闲区（To）。
    

**4. 对象晋升老年代（Tenuring）的场景**

在 Minor GC 过程中，存活对象并不总是留在 Survivor 区，出现以下情况时会被提升（Promote）到老年代：

- **达到年龄阈值**：对象的 GC 年龄达到设定上限（HotSpot 默认最高为 **15**，可用 `-XX:MaxTenuringThreshold` 调整）。
    
- **动态年龄判定**：Survivor（To）区中相同年龄所有对象大小的总和大于 Survivor 空间的一半（50%），大于等于该年龄的对象直接进入老年代。
    
- **大对象直接入老年代**：若某个新对象占用内存过大（超过 `-XX:PretenureSizeThreshold`），它不会进入 Eden，而是直接分配在老年代。
    
- **空间分配担保机制**：Minor GC 后 Survivor（To）区装不下剩余的存活对象时，多余对象会通过担保机制直接存入老年代。
    

**5. Minor GC 与 Major GC / Full GC 的对比**

| **维度**   | **Minor GC (Young GC)** | **Major GC / Full GC**             |
| -------- | ----------------------- | ---------------------------------- |
| **回收区域** | 仅新生代（Eden, S0, S1）      | 老年代（Major） / 整个 Java 堆 + 元空间（Full） |
| **触发频率** | 非常频繁                    | 频率较低                               |
| **执行耗时** | 短（通常几毫秒到几十毫秒）           | 长（通常是 Minor GC 的 10 倍以上）           |
| **回收算法** | 复制算法                    | 标记-清除 或 标记-整理 算法                   |
