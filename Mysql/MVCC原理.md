# InnoDB MVCC 面试笔记

## 一、MVCC 是什么，解决什么问题

**MVCC（Multi-Version Concurrency Control，多版本并发控制）**：InnoDB 通过为每行数据保存多个历史版本，让"读"操作不需要加锁就能拿到一个逻辑上一致的快照，从而实现**读写不阻塞**、提升并发。

**边界要划清楚**：MVCC 只作用于"读-写"并发场景（即快照读），不解决"写-写"冲突。两个事务同时 update 同一行，走的是行锁，跟 MVCC 无关。面试很多人会把 MVCC 说成"万能并发方案"，这是错的。

---

## 二、先搞清楚背景：隔离级别与并发问题

|问题|定义|
|---|---|
|脏读|读到别的事务**未提交**的修改|
|不可重复读|同一事务内，两次读同一行结果不一样（因为别的事务改了并提交了）|
|幻读|同一事务内，两次范围查询，多/少了几行（因为别的事务插入/删除了并提交了）|

InnoDB 默认隔离级别是 **REPEATABLE READ（RR）**，标准 SQL 规范里 RR 应该还是会有幻读，但 InnoDB 通过 **MVCC + Next-Key Lock** 组合，把幻读也基本解决了（细节见第六节）。

---

## 三、MVCC 三大核心组件

```
1. 每行记录的隐藏字段
2. Undo Log 版本链
3. Read View（一致性视图）
```

### 1. 隐藏字段

| 字段          | 长度  | 说明                              |
| ----------- | --- | ------------------------------- |
| DB_TRX_ID   | 6字节 | 最近一次插入/修改该行的事务ID                |
| DB_ROLL_PTR | 7字节 | 指向 undo log 里这一行的上一个版本，串成版本链    |
| DB_ROW_ID   | 6字节 | 只有表没有主键、也没有唯一非空索引时才会生成，用作隐藏聚簇索引 |


**注意**：不是每行都有 DB_ROW_ID，这是条件生成的，很多资料讲错。

**delete 的真相**：不是物理删除，是打上 delete_mark 标记 + 更新 DB_TRX_ID，真正的物理清除交给后台 purge 线程。

### 2. Undo Log 版本链

每次修改一行，旧版本不会被覆盖，而是写进 undo log，通过 DB_ROLL_PTR 串成一条链表，新版本在链头，越往后越旧。

**两种 undo log 的生命周期不同**：

- **insert undo log**：只在事务回滚时可能用到，事务一提交就能立刻删掉。
- **update undo log**：不仅用于回滚，MVCC 构造历史版本也要靠它，所以**不能随事务提交立刻删除**，必须等 purge 线程确认没有任何活跃事务还需要它。

这直接导致一个重要结论：**长事务会让大量 update undo log 无法被清理，版本链越拉越长（查询要沿链回溯，变慢），同时回滚段空间不断膨胀，是生产环境的经典性能隐患**。这一点面试主动提到会加分。

### 3. Read View（重点中的重点）

Read View 是判断"某个版本是否对当前事务可见"的依据，包含四个字段：

- **m_ids**：生成时系统里"活跃未提交"的事务ID列表
- **min_trx_id**：m_ids 里的最小值
- **max_trx_id**：系统下一个要分配的事务ID（不是"当前最大值+1"这种粗糙说法）
- **creator_trx_id**：创建这个 Read View 的事务自己的ID

---

## 四、最核心的一点：Read View 什么时候生成，决定了 RC 和 RR 的区别

这是整个 MVCC 里最容易被问倒、也最能体现理解深度的一点：

- **READ COMMITTED（RC）**：**每次**快照读都重新生成一个 Read View → 每次都能看到别的事务最新提交的结果 → 导致不可重复读。
- **REPEATABLE READ（RR）**：**只在事务内第一次**快照读时生成一次，之后整个事务复用同一个 Read View → 同一事务内看到的数据是"定格"的 → 可重复读。

**一句话记忆**：RC 和 RR 底层用的是同一套 MVCC 机制，唯一的区别就是 Read View 的生成频率。这也是面试官最爱追问的点。

---

## 五、可见性判断算法（完整且正确的顺序）

拿到某行的某个版本，判断它对当前事务是否可见，按顺序判断：

```
第0步：trx_id == creator_trx_id？
  → 是自己在本事务里改的，直接可见
  （这一步很多资料会漏掉，但没有它逻辑上是有漏洞的：
    事务不可能看不到自己刚做的修改）

第1步：trx_id < min_trx_id？
  → 生成 Read View 时这个事务已经提交了，可见

第2步：trx_id >= max_trx_id？
  → 这个版本是 Read View 生成之后才出现的事务改的，不可见
  → 顺着 undo log 找上一个版本，回到第0步重新判断

第3步：min_trx_id <= trx_id < max_trx_id？
  → 再看 trx_id 是否在 m_ids 里
     在  → 生成时这个事务还没提交 → 不可见 → 找上一版本
     不在 → 生成时已经提交了     → 可见
```

**举例**（可以直接背下来当案例讲）：

```
表中原始数据：name=张三, trx_id=100

事务A开启，第一次查询 → 生成 Read View，m_ids=[200]（假设此时事务B已经开始但未提交）

事务B执行：update ... set name='李四'; commit;
  → 生成新版本：name=李四, trx_id=200

事务A再次查询（RR级别，复用同一个Read View）：
  拿到最新版本 trx_id=200
  → 200 在 m_ids 里 → 生成时未提交 → 不可见
  → 沿undo log找上一版本：name=张三, trx_id=100
  → 100 < min_trx_id(200) → 可见

结论：事务A两次都看到"张三"，实现了可重复读。
```

## 六、快照读 vs 当前读，以及幻读到底怎么防住的

|类型|举例|走不走 MVCC|加不加锁|
|---|---|---|---|
|快照读|普通 `select`|走|不加锁|
|当前读|`select...for update`、`select...lock in share mode`、`update`、`delete`、`insert`|不走，永远读最新数据|加行锁/间隙锁|

### 幻读的完整答案（原本"部分解决"这种说法不够准确）

- **快照读场景下**：RR 级别因为 Read View 只生成一次，天然就不会看到其他事务后来插入的新行 —— **这部分幻读是纯靠 MVCC 解决的**，不需要额外加锁。
- **当前读场景下**：当前读根本不走 MVCC，必须靠 **Next-Key Lock（Record Lock + Gap Lock）** 物理锁住"行之间的间隙"，阻止别的事务插入新行，才能保证当前读两次结果一致。

举例：

```
表中数据 id = 5, 10, 15

事务A：select * from t where id > 5 and id < 15 for update;
  → InnoDB 锁住 (5,10] 和 (10,15) 的间隙 + 记录10本身

事务B：insert into t values(8);
  → 被 Gap Lock 阻塞，直到事务A提交
```

**准确说法应该是**："MVCC 解决了快照读下的幻读，Next-Key Lock 解决了当前读下的幻读，两者配合才让 RR 整体上规避了幻读"，而不是笼统一句"部分解决"。

---

## 七、MVCC 解决问题总览

|问题|快照读|当前读|
|---|---|---|
|脏读|✅ MVCC|✅ 锁天然不读未提交数据|
|不可重复读|✅ MVCC（RR下Read View只建一次）|✅ 行锁保证不被并发修改|
|幻读|✅ MVCC（Read View复用，看不到新插入行）|需要 Next-Key Lock，MVCC本身管不了|

## 八、面试话术（背诵版，覆盖三层追问）

**Q1：InnoDB的MVCC是怎么实现的？**

> 通过隐藏字段（DB_TRX_ID记录最近修改的事务ID，DB_ROLL_PTR指向历史版本）、Undo Log版本链和Read View三部分实现。数据修改时旧版本写入undo log并通过回滚指针串成链表，事务执行快照读时生成Read View（记录当时活跃未提交的事务列表），通过比较记录的trx_id和Read View信息判断版本可见性——先判断是不是自己的修改，再判断是否在活跃事务范围内，不可见就沿undo log链继续回溯，直到找到可见版本。

**Q2：RC和RR在MVCC实现上的区别是什么？**

> 区别在Read View的生成时机：RC每次快照读都重新生成，所以能看到别的事务已提交的最新结果，导致不可重复读；RR只在事务第一次快照读时生成一次并复用，所以同一事务内多次读结果一致。

**Q3：MVCC能完全解决幻读吗？**

> 不能，只解决快照读场景下的幻读。当前读（for update/更新/删除）不走MVCC，要靠Next-Key Lock（记录锁+间隙锁）锁住数据间隙防止插入，才能避免当前读下的幻读。

**Q4（加分项）：undo log什么时候删除？长事务有什么危害？**

> update类型的undo log提交后不能立刻删，因为MVCC可能还要用它构造历史版本，得等后台purge线程确认没有活跃事务还需要它才会清理。长事务会导致大量旧版本undo log无法purge，版本链变长查询变慢，回滚段还会不断膨胀，是生产环境常见的性能隐患。
