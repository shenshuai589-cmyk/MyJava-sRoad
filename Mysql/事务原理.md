
事务（Transaction）是数据库中**一组操作的集合**，这些操作要么全部成功，要么全部失败回滚，保证数据的一致性。

例如转账：

```
-- A账户减少100
update account set money = money - 100 where id = 1;

-- B账户增加100
update account set money = money + 100 where id = 2;
```

这两个操作必须同时成功，否则会出现：

- A扣钱成功，B没收到钱 ❌
- B收到钱，A没扣钱 ❌

所以需要事务。

---

# 一、事务的四大特性 ACID

## 1. 原子性 Atomicity

> 事务是不可分割的最小操作单位，要么全部成功，要么全部失败。

例如：

```
转账事务：

扣钱 √
加钱 ×

结果：
扣钱操作撤销
恢复原来的金额
```

实现：

**Undo Log（回滚日志）**

---

## 2. 一致性 Consistency

> 事务执行前后，数据库必须保持一致状态。

例如：

转账前：

```
A账户 1000
B账户 1000

总金额 = 2000
```

转账：

```
A -100
B +100
```

之后：

```
A账户 900
B账户 1100

总金额 = 2000
```

一致性没有被破坏。

注意：

一致性是事务最终目的。

其他三个特性都是为了保证一致性。

---

## 3. 隔离性 Isolation

> 多个事务同时执行时，事务之间互不干扰。

例如：

事务A：

```
select money from account where id=1;
```

事务B：

```
update account set money=500 where id=1;
```

隔离性保证：

事务A不会读到事务B没有提交的数据。

实现：

- 锁机制
- MVCC

---

## 4. 持久性 Durability

> 事务提交后，对数据的修改永久保存。

例如：

```
commit;
```

提交后：

即使：

- MySQL宕机
- 服务器重启

数据仍然存在。

实现：

**Redo Log（重做日志）**

---

# 二、事务执行流程（重点）

InnoDB事务执行：

```
SQL
 |
 |
修改Buffer Pool
 |
 |
写Redo Log Buffer
 |
 |
事务提交
 |
 |
Redo Log刷盘
 |
 |
数据持久化
```

例如：

执行：

```
update user set age=20 where id=1;
```

实际上不是直接修改磁盘。

流程：

```
磁盘数据页

     ↓

加载到Buffer Pool

     ↓

修改内存中的数据页

     ↓

记录Redo Log

     ↓

commit

     ↓

Redo Log刷入磁盘
```

---

# 三、为什么需要Redo Log？

假设没有Redo Log：

修改数据：

```
内存修改
 ↓
直接写磁盘
```

如果：

```
修改10000条数据
```

每次都写磁盘：

效率非常低。

所以：

MySQL采用：

> WAL（Write Ahead Logging）预写日志技术

即：

先写日志，再写数据。

流程：

```
修改数据

 ↓

写Redo Log

 ↓

提交事务

 ↓

后台慢慢刷新数据页
```

---

# 四、Redo Log（保证持久性）

## 作用

保证：

> 已提交事务的数据不会丢失

例如：

事务：

```
update account 
set money=900 
where id=1;
```

提交：

```
commit;
```

突然：

```
服务器断电
```

恢复时：

MySQL读取：

```
Redo Log
```

重新执行：

```
money=900
```

恢复数据。

---

# 五、Undo Log（保证原子性）

作用：

> 保存修改前的数据，用于回滚

例如：

执行：

```
update user
set age=20
where id=1;
```

修改前：

```
age=18
```

Undo Log保存：

```
id=1
age=18
```

如果：

```
rollback;
```

恢复：

```
age=18
```

---

# 六、事务提交过程（面试重点）

InnoDB采用：

## 两阶段提交（2PC）

为什么？

因为：

Redo Log

和

Binlog

需要保持一致。

流程：

```
执行SQL

↓

写Undo Log

↓

修改Buffer Pool

↓

写Redo Log

↓

Redo Log进入prepare状态

↓

写Binlog

↓

Redo Log提交commit状态

↓

事务完成
```

图：

```
        SQL执行

           |
           ↓

      Buffer Pool

           |
           ↓

      Redo Log
        prepare

           |
           ↓

        Binlog

           |
           ↓

      Redo Log
        commit
```

# 七、事务隔离级别

MySQL支持4种：

|隔离级别|脏读|不可重复读|幻读|
|---|---|---|---|
|读未提交|√|√|√|
|读已提交|×|√|√|
|可重复读|×|×|√|
|串行化|×|×|×|

# 八、MySQL默认隔离级别

MySQL InnoDB：

默认：

```
REPEATABLE READ
可重复读
```

原因：

InnoDB通过：

```
MVCC
+
Next-Key Lock
```

解决幻读。

---

# 九、MVCC事务原理（重点）

MVCC：

Multi-Version Concurrency Control

多版本并发控制。

核心：

每条数据隐藏字段：

```
DB_TRX_ID
最后修改事务ID

DB_ROLL_PTR
回滚指针
```

例如：

原数据：

```
name=张三
```

事务A修改：

```
name=李四
```

产生版本链：

```
当前数据

name=李四
trx_id=200

     |
     ↓

Undo Log

name=张三
trx_id=100
```

查询时：

根据事务视图选择版本。

# 十、事务隔离靠什么实现？

总结：

|问题|解决方案|
|---|---|
|原子性|Undo Log|
|持久性|Redo Log|
|隔离性|锁 + MVCC|
|一致性|ACID共同保证|

# 十一、面试回答模板

面试官：

> MySQL事务原理是什么？

回答：

> MySQL事务通过ACID保证数据可靠性，其中原子性通过Undo Log实现，持久性通过Redo Log实现，隔离性通过锁机制和MVCC实现。一条SQL执行时会先修改Buffer Pool中的数据页，同时记录Redo Log和Undo Log，事务提交时采用两阶段提交保证Redo Log和Binlog一致。如果发生故障，可以通过Redo Log恢复已提交事务，通过Undo Log进行事务回滚。
